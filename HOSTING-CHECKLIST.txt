Launch decision: NOT READY FOR A PUBLIC LAUNCH

This is a practical setup guide, not a promise that a deployment is production-ready.
Complete every STOP item below before inviting the public or accepting listings.

WHAT IS IN THE PROJECT NOW
--------------------------
- Next.js application with published-only property search and free-browsing/free-viewing messaging.
- Supabase email/password and Google sign-in/sign-up flows for tenant and landlord roles.
- Draft `/privacy`, `/terms`, and `/retention` pages; footer links and unchecked signup policy acknowledgement.
- A database-side policy-acceptance audit table/trigger is defined in `docs/schema.sql` but still needs a backed-up, live Supabase application and test.
- Landlord availability choices for Available, Soon available, and Taken; public search excludes Taken homes.
- Landlord content edits return published submissions to review; soon-available date and last-confirmed timestamp are available.
- Authenticated tenant viewing-request/report flows, landlord request management, saved-search filters, and account data export/privacy request endpoints are implemented.
- Basic uptime probe exists at `/api/health`; no external monitoring or notification provider is configured.
- Authenticated tenant and landlord dashboard routes.
- Protected `/admin` moderation centre for allowlisted, confirmed Google accounts; it requires
  server-only `ADMIN_EMAILS` and `SUPABASE_SERVICE_ROLE_KEY` configuration and migration 002
  on databases that already have the earlier schema.
- Secure-cookie options: production auth cookies are HttpOnly, Secure, SameSite=Lax.
- Database schema template for profiles, listings, viewing requests, and listing interactions.
- Signed-in property activity logging, with participant-only row policies and an account rate limit.
- OpenStreetMap click-to-select map pins, 2/5/10 km nearby search, approximate public
  listing pins, and database-side radius filtering (not yet tested against live Supabase).
- Customer care phone and WhatsApp link: 0758 934 463 / +254 758 934 463.
- Wizard drafts are account-scoped and local; submitted listings and compressed photos are stored in Supabase and remain private pending review.
- M-Pesa is deliberately disabled. The app must not claim a payment succeeded.
- Clean `npm ci`, `npm audit` (zero advisories), `npx tsc --noEmit`, and `npm run build`
  completed after stopping the existing local Next.js server.
- Public/auth setup pages and the unauthenticated dashboard redirect passed smoke checks.

RECOMMENDED HOSTING SHAPE
-------------------------
- Web app: Vercel (connect a Git repository; this workspace is not currently a Git repo).
- Database and authentication: Supabase project in an appropriate region.
- Domain/DNS: a domain you control, with HTTPS enabled by the hosting provider.
- Email: a production transactional SMTP provider configured through Supabase Auth.
- Maps: OpenStreetMap raster tiles with visible attribution; review the tile usage policy
  and use a compliant hosted tile provider if expected traffic exceeds the public service's
  permitted usage. No Google Maps API key is required.
- Images: private Supabase Storage bucket `listing-photos`, WebP-only uploads up to 2 MB,
  owner-scoped upload/delete policies, random object names, signed image delivery, and
  database approval gating. Do not upload identity documents or expose service-role
  secrets in browser-visible variables.
- Monitoring: hosting error logs, Supabase database/auth monitoring, uptime alert, backups,
  and a named person who responds to alerts.
- Basic uptime URL: `https://YOUR_DOMAIN/api/health`. This only confirms the web process is
  responding; it does not test Supabase, email, or storage.

A provider's free tier, storage/egress limits, backup retention, region availability, and
terms can change. Check current provider limits and costs before selecting a plan.

1. CLEAN LOCAL INSTALL AND BUILD
-------------------------------
1. If the development server is using this workspace, stop it from the terminal/session
   that started it before replacing dependencies. Do not terminate an unrelated process.
2. From the project root, run:

      npm ci
      npm audit
      npm run build

3. Do not deploy if npm ci, npm audit, or npm run build fails. Record the complete error,
   fix it, and rerun all three commands.
4. Start a local production server with `npm run start` and perform the smoke tests below.
5. Commit package.json and package-lock.json together only after a clean install and build.
   Never deploy with a lockfile that has not been tested by npm ci.

2. CREATE AND CONFIGURE SUPABASE
--------------------------------
1. Create a Supabase project; choose a region appropriate for your users and review its
   privacy, backup, recovery, compute, storage, and billing settings.
2. Back up the project, then apply reviewed SQL: use `docs/schema.sql` only for a fresh
   project; use `supabase/migrations/202610070001_launch_workflows.sql` for the existing
   project that already has the prior baseline schema. Test on staging first and confirm
   the migration finishes without errors.
3. In Table Editor/API settings, verify Row Level Security is enabled on profiles, listings,
   listing_images, viewing_requests, listing_reports, and listing_interactions.
4. Create test tenant and landlord accounts. Confirm each receives exactly one profile
   row and that a user cannot read or change another user's profile or interaction rows.
5. Test database policies with tenant, landlord, and unauthenticated sessions. Verify a
   landlord cannot modify another landlord's listing and a tenant cannot see another
   tenant's activity. Do not use the Supabase service-role key in this Next.js app.
6. Keep database backups enabled and test a restore procedure before launch. Apply schema
   changes later as versioned migrations and take backups before migrations.

3. CONFIGURE EMAIL AND GOOGLE SIGN-IN
-------------------------------------
1. Copy `.env.example` to `.env.local` for local development. Set:

      NEXT_PUBLIC_APP_URL=http://localhost:3000
      NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
      NEXT_PUBLIC_SUPABASE_ANON_KEY=YOUR_SUPABASE_PUBLISHABLE_OR_ANON_KEY

   These two Supabase client settings are public identifiers/keys; database access must
   still be protected by RLS. Never add a service_role key or database password to code.
2. In Supabase Auth, set the local Site URL and allow-list
   `http://localhost:3000/auth/callback` and `http://localhost:3000/auth/reset`.
3. Configure Google OAuth in Google Cloud Console. Set the Google OAuth callback/redirect
   URI to the exact Supabase Auth callback shown by the Supabase Google provider settings
   (normally `https://YOUR_PROJECT_REF.supabase.co/auth/v1/callback`). Add the Google
   client ID/secret only in the Supabase provider settings.
4. In Google OAuth, configure the production app name, support email, authorized origins,
   and privacy/terms URLs. Test both first-time sign-up and returning-user sign-in.
5. Configure a production SMTP sender in Supabase Auth. Set SPF, DKIM, and DMARC for the
   sending domain; test confirmation and password-recovery emails, spam placement, expiry,
   one-use links, and resend behaviour.
6. Add production Site URL and exact redirect allow-list entries, for example
   `https://YOUR_DOMAIN/auth/callback`. Remove obsolete preview URLs when no longer needed.
7. Test that selecting Landlord creates a landlord profile, selecting Tenant creates a
   tenant profile, existing Google accounts keep their original role, and unauthenticated
   users cannot access either dashboard.

1. Put the reviewed source in a private GitHub repository and push the tested branch. The

2. Import that repository into Vercel; use the Next.js framework preset and the default

5. Add the custom domain in Vercel, configure the exact DNS records it provides, wait for

MANUAL MODERATION FALLBACK (IF THE ADMIN SCREEN IS UNAVAILABLE)
---------------------------------------------------------
1. Restrict Supabase project/SQL-editor access to named staff with MFA; never grant
   moderation access to landlords or tenants.
2. Inspect the pending listing, confirm landlord identity/ownership and consent, verify
   property details and photos, and reject suspicious or misleading submissions.
3. Only after approval, run a reviewed SQL transaction as a database administrator,
   replacing the UUID with the verified listing ID:

      BEGIN;
      UPDATE public.listing_images
        SET is_approved = true
        WHERE listing_id = 'LISTING_UUID';
      UPDATE public.listings
        SET current_status = 'published',
            published_at = NOW(),
            updated_at = NOW()
        WHERE id = 'LISTING_UUID'
          AND current_status = 'pending_review'
          AND is_demo = false;
      COMMIT;

4. Verify exactly the intended listing was updated and that its public detail page and
   signed images work. If approval fails, ROLLBACK and investigate; do not use a landlord
   account to publish.
